ESP32 Tamagotchi

A virtual pet dragon that lives on a bare ESP32 dev board. The board keeps it alive, saves it to flash, and serves its LCD screen as a web page on my home Wi-Fi. No extra parts, and it picks up where it left off after being unplugged.

I had an ESP32 dev board with nothing attached to it: a dual-core 240 MHz chip, 520 KB of RAM, 4 MB of flash, Wi-Fi, one button and one LED. That's far too little memory for Linux, but plenty for something small that lives entirely on the board.

So it runs a pet. Plug the board into any USB charger and a dragon comes back to life. Open boardpet.local on a laptop and you get its screen: feed it, play with it, clean up after it, put it to bed. It hatches from an egg, grows up over a few days, and gets hungry while you're away, even if the board was unplugged the whole time.

One loop, six jobs

The board runs MicroPython, which starts main.py on every power-up. There are no threads to lean on, so everything shares one asyncio loop: the web server, a Wi-Fi reconnect loop, the internet clock, a once-a-second simulation tick, the LED blink pattern and the BOOT button. Each task yields often enough that a page request never waits on the others.

The page is a single HTML file with its CSS and JavaScript inline. The dragon is drawn on a canvas from bitmaps written as strings, one per growth stage, mirrored when it turns around. Gzipped, the whole page is 5.9 KB, and the board streams it in 1 KB chunks so it never holds the file in RAM.

The pet's rules live in a separate file with no hardware imports. The same pet.py runs on the board, in 11 desktop tests, and behind a mock server I used to work on the page without flashing anything.

Time while it's unplugged

The ESP32 has no clock battery. Pull the plug and it forgets what time it is, so on its own it can't know whether it was off for a minute or a week. Every save records the time, and on boot the board gets the real time from the internet over NTP. It works out when it booted (now minus its uptime), takes the gap since the last save, and replays that gap through the simulation in one-minute steps, capped at seven days.

My first version got this wrong in a way that only showed up on real hardware. Before the clock syncs, the pet still runs on the chip's internal timer, and those seconds were meant to be subtracted from the gap so they wouldn't count twice. But it subtracted the seconds from the current boot, which aren't part of the gap at all. After a hard reset the board reported being unplugged for −27 seconds. The fix was to subtract only what the previous run had simulated without a clock.

To test it without waiting hours, I rewound the saved timestamp by three hours and hard-reset the board:

BoardPet starting: Patrick egg wifi up: http://boardpet.local (10.0.0.214) clock set (2026, 11, 19, 19, 45, 11, 3, 323) unplugged for 10803.0 s after: age 3.05h stage hatchling hunger 43

The egg had hatched and hunger had dropped from 80 to 43, which matches the rates: hunger empties in about eight hours, and nothing drains while it's still an egg.

Sick, never dead

Real Tamagotchis die. This one doesn't: I wanted unplugging it for a week to feel like coming home to a grumpy pet, not a funeral. The meters stop at zero. If one stays there for an hour, or three poops pile up, the dragon gets sick, the LED on the board blinks fast, and happiness drains twice as quickly until it gets medicine. Asleep, everything drains four times slower while energy refills.

Saving without wearing out the flash

Flash memory wears out with writes, so the board doesn't save every second. It saves after every action and every five minutes. Losing up to five minutes of idle time on a power cut costs nothing, because the next boot replays from the last saved timestamp anyway. Each save writes to a temporary file and renames it over the old one, so pulling the plug halfway through a write leaves the previous save intact instead of a corrupt one.
