Duely

Duely turns a student's Brightspace calendar into a clean Google Calendar: deadlines once instead of three times, tests moved when a prof's announcement says so, and a chat that answers "what's due this week?". It runs in the student's own Google account, so it keeps syncing with the laptop closed, and it uses whichever AI they already have.

Brightspace's calendar feed is noisy. Every quiz shows up three times (opens, closes, due), course content "becomes available" every week, and when a prof moves a midterm it's usually only in an announcement. I'd built a version of this for myself first, hard-wired to my school, my Google project and my API key. Duely is that engine rebuilt so any student can install it, with no server of mine in the middle.

TypeScript: one engine, three places

Why The sync engine (parsing the feed, merging the three copies of each quiz, deciding what changed) already existed in TypeScript. The same code had to run on the desktop, inside Google Apps Script and in tests, and one language for all three meant one engine instead of three that drift apart.

The struggle Apps Script isn't Node or a browser. It has no fetch, no Intl, no URL, no timers and no Web Crypto, and every time zone calculation in the engine leaned on Intl.

The fix I pulled every host feature behind a small swappable service: time zone offsets, SHA-1, query strings, HTTP. The desktop plugs in Node's versions; the Apps Script build plugs in Utilities and UrlFetchApp. A build step bundles everything into one ~130 KB file, and a test runs that bundle in a sandbox with all of those globals deleted. It fails if the script writes a single calendar event differently from the desktop app.

Electron: one installer per system

Why Students use Windows, Macs and Linux, and the engine is TypeScript, so Electron let the desktop app run the engine directly with one codebase for all three.

The struggle The failures were all quiet ones. The sandboxed preload script was built as an ES module, which Electron doesn't load there, so the window had no bridge to the app and nothing said why. On Linux desktops without a notification service, every notification froze the app for about 25 seconds. And on Linux without a keyring, Electron can't encrypt saved keys at all.

The fix Each one got a check that would have caught it. The packaged smoke test now fails if the bridge isn't there, and it runs on Windows, macOS and Linux in GitHub Actions before any release is drafted. Duely asks D-Bus whether a notification service exists before sending one. Without a keyring, Duely still works but says plainly that keys are only lightly protected, and once a keyring shows up it moves the saved keys into it by itself.

Google Apps Script: syncing with the laptop closed

Why A desktop app only syncs while it's open. The usual fix is a server, which costs money every month and would mean I hold every student's calendar access and AI key. Apps Script runs code inside the student's own Google account, on a timer, for free, and nobody else can see it.

The struggle The desktop app needs to talk to the script, and the obvious way, a private web app, rejects the call unless the student also grants Google Drive access, which is far too much to ask. Calling the Calendar API from the script failed with a 403, because the script's hidden Cloud project doesn't have it enabled. And one line that referenced Node's process only crashed once it ran in Apps Script for real.

The fix The web app is open to anonymous calls but answers nothing without a 256-bit key that only the student's desktop has, checked in constant time. Calendar writes go through Apps Script's built-in Calendar service instead of the REST API. Only the script writes to the calendar: when you tick something off in the app, it goes into an inbox the script picks up next run, so the two never fight over an event. A full sync takes under six seconds; when nothing changed, about two.

Google Calendar and sign-in

Why Google Calendar is what students already have on their phones. Duely asks for the narrowest permission Google offers, calendar.app.created: it can only see the one calendar it creates, never your other ones.

The struggle Each student brings their own Google sign-in client, and Google signs a client in "Testing" out every seven days. The standard advice is to publish the client, but that's buried behind Google Cloud's branding forms.

The fix I looked at what actually needs that sign-in. Once the script is installed, it runs on its own authorization, so the desktop only needs Google when a new version updates the script. An expired sign-in now just waits for a one-click Reconnect, and nothing stops syncing in the meantime.

Bring your own AI

Why Paying for my own AI calls on behalf of every student wasn't an option, and holding their keys was worse. So students bring one key: OpenAI, Anthropic, Gemini (which has a free tier), Mistral, Groq, or a model running on their own computer. Duely has adapters for OpenAI-compatible APIs, Anthropic and Gemini, and the key never leaves the student's machine and Google account.

The struggle Models get renamed, overloaded and retired, and nobody should have to know what gemini-flash-lite-latest means. Worse, a live test caught a bug the offline tests couldn't: newer Gemini models reject a conversation unless each tool call comes back with its "thought signature". Duely was dropping it, so any answer that needed a second step quietly fell back to the rules, and it looked like the AI was working.

The fix Duely asks the provider which models the key can use and tries small, fast ones, skipping any that are overloaded or gone. The adapter passes the signature through, and the live score went to 148 of 150. Every answer is checked against the calendar before it's shown; a date or item that isn't there sends the AI back to try again. If the AI is down, a rule-based parser answers instead, and it passes all 811 questions in the test set.

Cloudflare Workers and Discord: alerts on your phone

Why If a prof moves a test while your laptop is shut, a desktop notification doesn't help. A Discord DM reaches your phone, and students set it up with one sign-in instead of creating a bot or webhook themselves.

The struggle Discord only lets a bot DM people it shares a server with, and a bot token can't ship inside an open-source app. That means a server in the middle, which I'd been avoiding, plus a public Discord server that strangers could wander into.

The fix A small Cloudflare Worker on the free tier holds the token. It stores only a hash of each device's token and the Discord user ID, never the text of an alert. The server has no invites: the only way in is Duely's own Connect Discord sign-in, an hourly sweep removes anyone without a link, and links unused for 30 days are deleted. The Apps Script calls the Worker directly, so the DM still arrives with the laptop off.

Your data

There's no Duely account. Settings and keys stay on your computer, encrypted with the system keychain, and the engine lives in your Google account, not mine. Releases are built and tested on all three systems by GitHub Actions, and the app updates itself from GitHub Releases. The privacy policy spells out what goes where.
